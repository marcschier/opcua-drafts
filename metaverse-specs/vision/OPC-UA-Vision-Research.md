# OPC UA — Vision — Research and design rationale

> **Companion research report to [`OPC-UA-Vision.md`](OPC-UA-Vision.md).** This document records the prior art that was surveyed before drafting, the four gaps that survey identified, and the design decisions those gaps forced. It is **informative**: nothing here is normative, and where a finding is uncertain it is flagged as such.
>
> Nothing in this repository is official, endorsed by the OPC Foundation, the Alliance for OpenUSD, EMVA, DMSC, IDTA or NVIDIA. Namespace URIs and NodeIds are provisional.

---

## 0 Why this document exists

The sibling specification *OPC UA — OpenUSD Bindings* cites a research report that was never committed alongside it, so the reference dangles. This report is committed **in the same folder as the specification it justifies**, and is linked relatively, so the repository link checker verifies it.

The survey behind it covered: the two released OPC UA machine vision companion specifications, the OPC UA robotics model, the OPC UA result-transfer and geometric-measurement models, the OPC UA Asset Administration Shell bridge, the GenICam/GigE Vision device stack, QIF and the metrology standards, the ROS 2 perception ecosystem, ONNX and the ISO/IEC AI standards, the IDTA submodel catalogue, and NVIDIA Isaac Sim / Omniverse Replicator.

## 2 The four gaps

### 2.1 Gap 1 — result semantics are explicitly undefined

Every result-bearing OPC UA specification surveyed types its result payload as `BaseDataType[]` and declines to define it.

- **OPC 40100-1 §12.17**, on `ResultDataType.ResultContent`: *"The structure of the ResultContent which is generated by the vision system is application-specific and not defined at this time."* The field is `BaseDataType[]` — the most abstract type in OPC UA — and it is **Optional**.
- **OPC 40100-1 §5**, on result transfer: *"The detailed data format of a result is not included in this specification."*
- **OPC 40100-1 §3.1**, on recipes: *"The actual content of the data structure is out of the scope of this specification."* Annex B.1.2.1 adds: *"Recipes are handled as binary objects."*
- **OPC 40001-101 §10.5** repeats the identical sentence for the generic Machinery result.
- **OPC 40210 §5.1.3** is the clearest statement of all: *"For geometric measurement results, many file formats and structures (e.g., AQDEF, DMIS [ISO 22093], QIF, I++ DMS, …) and other generic formats (CSV, raw text, JSON, XML …) are used… Therefore, this Companion Specification defines only the transport and the management of the result."*

That last quotation matters because it is not an oversight — it is a considered decision to name the content standards and then **not** map them. Two vendors can both be fully conformant to OPC 40100-1 and produce mutually unintelligible results.

**Design consequence.** The Vision model defines result content: `VisionCharacteristicDataType` for inspection and `VisionDetectionDataType` for perception. This is the specification's principal contribution, and it is the one place where it deliberately does what the existing specifications declined to do.

### 2.2 Gap 2 — no imaging parameters anywhere

OPC 40100-2 (2024) models a vision system's physical bill of materials in real depth — and then stops exactly where imaging begins.

- `ILensType` (§9.7) is genuinely rich: `FocalLength`, `Aperture`, `Resolution` (lp/mm), `ModulationTransferFunction`, `BackFocalLength`, `MinimumWorkingDistance`, `Magnification`, `WorkingDistance`, `OpticalFormat`, `MountType`, `LensType`.
- `ILampType` (§9.12) provides `Wavelength`, `RelativeIntensity`, `Quality`, `LampType`.
- **`VisionImageSensorType` (§9.14) implements only the generic `IVisionInfoType` and adds zero members.** `VisionFrameGrabberType` (§9.15) is identical.

There is no resolution, pixel format, bit depth, exposure, gain, binning, region of interest, frame rate or interface bandwidth modelled anywhere in OPC UA. The camera — the single most important component of a vision system — is reduced to a nameplate.

A scan of the full OPC 40100-2 NodeSet and its normative reference list found **zero** occurrences of `GenICam`, `SFNC`, `GenTL`, `EMVA`, `GigE`, `CoaXPress`, `ExposureTime` or `PixelFormat`. Its normative references are OPC 10000-1…-8, OPC 10000-100, OPC 40001-1, OPC 40010-1 and SEMI E10-0312.

> **Uncertainty flagged.** One web source claimed OPC 40100-2 incorporates GenICam. Primary sources — the specification text and the NodeSet XML — contradict this. The primary sources were followed.

**Design consequence.** `ImageSensorType` carries SFNC 2.8-named acquisition parameters and PFNC-named pixel formats. The names are borrowed deliberately so a GenICam bridge is mechanical, but no dependency is taken.

### 2.3 Gap 3 — no AI, anywhere

There is **no released OPC UA companion specification for AI, machine learning, model deployment, inference, training data or model lifecycle.**

The OPC Foundation formed an "OPC UA for AI" working group (announced 22 April 2024), but its mandate is inverted relative to what a vision specification needs: it makes OPC UA information models consumable **by** AI tooling — RAG pipelines, MCP servers, engineering copilots — rather than describing AI **inside** the address space. Its principal output has been the conversion of 430+ companion specifications into machine-readable form.

OPC UA FX (Parts 80–84) adds deterministic TSN transport. That is a valuable *substrate* for feeding AI systems, not an AI standard.

Within OPC 40100-2, `IComputingDeviceType` (§9.1) exposes only free-form strings — `OperatingSystemInfo`, `DriverInfo`, `SoftwareImageInfo`, `PatchLevel`, `MassStorageState`, `RAMState`, `BatteryState`. There is no GPU, NPU, accelerator, VRAM or compute-capability typing: a GPU inference server and a CPU-only industrial PC are modelled identically. Software components defer to the DI `SoftwareType`, which has no ML-specific fields.

**Design consequence.** The Vision model adds `AiModelType`, `AiDatasetType`, `AiDeploymentType`, `InferencePipelineType` and `LearningJobType`, plus `VisionInferenceLocationEnum` and `VisionAcceleratorKindEnum`.

### 2.4 Gap 4 — robot vision does not exist in OPC UA

OPC 40010-1 v1.02 defines 25 ObjectTypes, 4 DataTypes and 7 ReferenceTypes. Every one is kinematic, control or safety related. Keyword scans of the NodeSet and documentation returned:

| Term | Result |
|---|---|
| `vision`, `camera`, `perception`, `hand-eye` | **zero occurrences** |
| `sensor` | only inside the §3.2 ISO 8373 definition text; not modelled |
| `TCP` / tool centre point | defined as a §3.2 *term*; **no TCP frame variable exists** |
| `calibration` | not found; no transforms, no frames |

The one extension point, `MotionDeviceType.AdditionalComponents`, is explicitly constrained by a §7.2.2 NOTE: *"From this specification, only instances of AuxiliaryComponentType and DriveType can be used in this container."*

Neither OPC 40010-1 nor OPC 40100-1 appears in the other's normative references. There is no joint working group, integration profile or roadmap document connecting them. Vision-guided robotics — bin picking, visual servoing — is undefined at the OPC UA standards level, and system integrators build it bespoke each time.

**Design consequence.** The Vision model adds `CoordinateFrameType` (ISO 9787 roles), `IntrinsicCalibrationType`, and `ExtrinsicCalibrationType` with an explicit `EyeInHand` / `EyeToHand` mount, plus 6-DoF poses on detections.

## 3 What the surrounding ecosystem provides

### 3.1 The device layer is solved — by GenICam, not by OPC UA

| Standard | Body | Version | Layer |
|---|---|---|---|
| GenICam (GenApi, **SFNC 2.8**, PFNC 2.4, GenTL 1.6, **GenDC 1.2**, GenCP) | EMVA | package 2025.10 | Device control API + feature naming |
| GigE Vision | A3 | **3.0** (April 2025; adds RDMA streaming) | Ethernet pixel transport |
| USB3 Vision | A3 | 1.2 | USB pixel transport |
| CoaXPress | JIIA | 2.1 | Coax pixel transport |
| EMVA 1288 | EMVA | Release 4.0 | Sensor characterization methodology |
| VDI/VDE/VDMA 2632 | VDI/VDE/VDMA | Blatt 1:2023-01, Blatt 2:2024-11 | Project specification and acceptance testing |

These are **complementary to** OPC UA, not competing with it, and the consortia coordinate explicitly through the G3 cooperation. The OPC Foundation's own scope text for OPC 40100-1 says the specification exists to *"complement or substitute existing interfaces"* and to *"create non-existent horizontal and vertical integration abilities"* — an acknowledgement that GenICam was never designed for factory integration.

No published GenICam-to-OPC-UA mapping specification exists. The VDMA Embedded Vision Study Group recommended introducing GenICam/SFNC into a future OPC UA companion specification, but that recommendation was never realised.

**Design consequence — the layering rule.** GigE Vision and GenDC carry pixels; OPC UA carries semantics and control. The Vision model therefore brokers **endpoints**, and its default media path keeps image bytes out of the OPC UA payload entirely. The inline `ByteString` facet is a bounded exception for single stills, gated on `MaxByteStringLength`, and is explicitly not a streaming path.

### 3.2 Inspection semantics are solved — by QIF, which OPC UA does not map

**QIF — Quality Information Framework**, governed by DMSC, standardised as **ISO 23952:2020** (also ANSI/QIF 3.0-2018), is an XML schema family: QIF Library, MBD, Plans, Resources, Rules, **Results**, Statistics.

QIF Results is characteristic-centric and carries exactly what an inspection verdict needs to be reproducible: nominal, actual, deviation, tolerance status, and **measurement uncertainty per ISO 14253**, with traceability to device, operator, timestamp, batch and CAD feature.

**No QIF OPC UA companion specification exists.** QIF can only travel as an opaque file through OPC 40001-101 with `FileFormat = "QIF"` — a label, not a semantic mapping. Academic work exists (Computers in Industry, 2022) but is research, not standard. Related standards DMIS (ISO 22093:2011) and I++ DME (VDMA 8722:2024-04) are likewise unmapped.

**Design consequence.** `VisionCharacteristicDataType` mirrors the QIF Results field set, uncertainty included, so a QIF document can be produced from a Vision result without inventing information. `VisionResultEvaluationEnum` includes `NotDecidable` for the case where uncertainty spans a tolerance limit.

### 3.3 Robot perception is solved — de facto, by ROS 2

| Concern | Artifact | Status |
|---|---|---|
| Governance | OSRA (Open Source Robotics Alliance), April 2024 | De facto |
| Current LTS | Jazzy Jalisco (May 2024 → May 2029) | De facto |
| Images and calibration | `sensor_msgs/Image`, `CameraInfo`, `PointCloud2` | De facto |
| Detections | `vision_msgs`: `Detection2D`, `Detection3D`, `ObjectHypothesisWithPose` | De facto |
| Planning with perception | MoveIt 2 with OctoMap | De facto |

Formally standardised alongside it: **ISO 9787:2013** (coordinate systems — world, base, mechanical-interface, **tool/TCP**, camera, object), **ISO 8373:2021** (vocabulary), **ISO 9283:1998** (performance test methods), **VDI/VDE 2634** (optical 3-D measuring systems).

**Explicit negative finding:** no ISO, IEC, VDI or ANSI standard governs the hand-eye calibration *procedure*. ISO 9787 defines which frames exist, not how to calibrate between them; the AX=XB formulation is academic in origin and every implementation is vendor-specific or a ROS community package. **ASTM WK78941** (bin-picking vision performance) is a work item, not yet published.

**Design consequence.** `VisionDetectionDataType` follows `vision_msgs` field naming so a bridge is mechanical. `ExtrinsicCalibrationType` carries the calibration *result* — transform, mount arrangement, residual — precisely because the *procedure* is unstandardised and only the outcome is portable.

### 3.4 AI description is solved — by the IDTA submodel templates

| Standard | Body | Identity |
|---|---|---|
| ONNX | LF AI & Data | Model interchange graph and operators |
| ISO/IEC 22989:2022 | ISO/IEC SC 42 | AI concepts and terminology |
| ISO/IEC 23053:2022 | ISO/IEC SC 42 | Framework for AI systems using ML |
| ISO/IEC 42001:2023 | ISO/IEC SC 42 | AI management system (certifiable) |
| ISO/IEC 23894:2023 | ISO/IEC SC 42 | AI risk management |
| **IDTA 02058-1-0** | IDTA | **Artificial Intelligence Dataset** |
| **IDTA 02059-1-0** | IDTA | **Artificial Intelligence Deployment** |
| **IDTA 02060-1-0** | IDTA | **Artificial Intelligence Model Nameplate** |

The three IDTA templates were published in **February 2025** and are currently the only standardised description of an industrial AI model. They are general-purpose rather than vision-specific, which makes them a good alignment target.

> **Conflicting evidence, resolved.** One line of research reported that no IDTA AI submodel template existed. A second found all three with specific IDTA numbers, repository paths and published PDFs. The second was better evidenced and was followed. Readers should re-confirm against the [IDTA submodel catalogue](https://industrialdigitaltwin.org/en/content-hub/submodels).

IDTA has **no** machine vision, camera or image inspection submodel template. The quality-adjacent ones are IDTA 02049 (Quality Control for Machining), IDTA 02032-1-0 (Inspection Documents of Steel Products) and IDTA 02065-1 (Digital Quality Documents). IDTA 02048 (Predictive Maintenance) explicitly excludes model internals.

The OPC UA bridge to the AAS, **OPC 30270 (I4AAS)**, maps to AAS **V2.0.1** and is slated for deprecation because AAS V3 is not backward compatible; a V3-aligned replacement is in development but unreleased.

**Design consequence.** `AiModelType`, `AiDatasetType` and `AiDeploymentType` align member-for-member with IDTA 02060/02058/02059 so an AAS can be populated from the address space without loss — while the Vision model itself stays standalone and takes no dependency on a bridge that is in flux.

### 3.5 Regulatory pressure

The **EU AI Act** (Regulation (EU) 2024/1689, in force 1 August 2024) makes an AI system automatically high-risk when it is a safety component of a product regulated under EU harmonisation legislation — which includes the Machinery Regulation (EU) 2023/1230 — and that product requires third-party conformity assessment. Deadlines: **2 December 2027** for Annex III standalone systems, **2 August 2028** for Annex I products. High-risk obligations include risk management, data governance, technical documentation, accuracy and robustness, human oversight, and **logging**. CEN/CENELEC JTC 21 is producing the harmonised standards, including prEN 18286.

Non-safety quality-inspection vision may fall outside Annex I; the classification is deployment-specific.

**Design consequence.** `VisionResultType` carries `ModelVersionUsed`, `Confidence` and `ExplanationUri`, and `AiModelType` carries `Digest` and `ProvenanceUri`, so that the "which model decided this, and on what basis" question is answerable from the address space rather than reconstructed from logs.

## 4 Why this belongs in `metaverse-specs/`

The decisive argument is **sim/real symmetry**.

NVIDIA Isaac Sim is an OpenUSD application. A simulated camera is a `UsdGeomCamera` prim; a real camera is a device. If both are described by the same information model, then synthetic data generation, model training and sim-to-real transfer share a contract with production inspection and robot guidance — and a client cannot tell, and need not tell, which it is talking to.

That symmetry only works if the scene model and the sensor model meet somewhere concrete. They meet at the **camera prim**, which is why this work also added `UsdGeomCameraType` to *OPC UA — OpenUSD Scene Materialization* (Part 2): its materialized UsdGeom subset previously covered Imageable, Xformable, Gprim, Mesh, Cylinder, Sphere, Cube, Cone and Capsule, but had **no camera**. The camera's aperture and focal-length attributes are simultaneously the USD scene description and the imaging intrinsics, which is exactly the intersection this specification needed.

The resulting division across the family:

| Concern | Specification |
|---|---|
| The camera prim exists in the address space, with intrinsics and pose | Part 2, `UsdGeomCameraType` |
| A live OPC UA value drives a camera property | Part 1, `OpenUsdLiveBindingType` |
| The sensor, its media endpoints, the AI, and the results | **This specification** |

## 5 Design decisions this evidence forced

| Decision | Driven by |
|---|---|
| Standalone, base-UA-only `RequiredModel` | Adoptability; and OPC 30270's deprecation shows the cost of hard-wiring to a moving target |
| Result content **is** defined | §2.1 — nobody else defines it |
| SFNC/PFNC naming, no GenICam dependency | §2.2, §3.1 — borrow the vocabulary, respect the layering |
| Media brokered as endpoints; RTSP and JPEG mandatory defaults | §3.1 — pixels belong out-of-band; a mandatory default guarantees interoperability |
| Inline `ByteString` clips gated on `MaxByteStringLength`, `Bad_EncodingLimitsExceeded` on overflow | Subscription convenience for one-image-per-part, without becoming a video path |
| QIF-shaped characteristics with uncertainty | §3.2 |
| `vision_msgs`-shaped detections with 6-DoF poses | §3.3 |
| Calibration carries the *result*, not the procedure | §3.3 — the procedure is unstandardised |
| `InferenceLocation` as an explicit property | §2.3 — on-server and off-server must share one result contract |
| IDTA 02058/59/60 alignment | §3.4 |
| Trust members on every result | §3.5 |
| Feedback path that also produces training labels | §2.3 — nothing else closes the loop |

## 6 Confidence and open questions

**High confidence** — verified against primary sources (specification text, NodeSet XML, the OPC Foundation reference site): the identity and versions in §1; the exact "not defined at this time" quotations; OPC 40100-2's empty image sensor type and absence of GenICam references; OPC 40010-1's complete absence of vision types; QIF's ISO 23952:2020 designation.

**Moderate confidence:** the IDTA AI template finding, where two research threads conflicted and the better-evidenced one was followed; OPC 30270's deprecation, which is stated on a working-group page without a formal notice date; GenApi's exact current version, which differs across sources.

**Open questions for the working group:**

1. Should `VisionCharacteristicDataType` carry a QIF `QPId` so a result can be joined to a QIF document, rather than only being structurally convertible?
2. Should the media endpoint model be factored out for reuse by any OPC UA specification that needs to broker a stream, rather than living in a vision specification?
3. When the AAS V3 companion specification lands, should the AI types reference it directly instead of only aligning by field name?
4. Is `Bad_EncodingLimitsExceeded` the right StatusCode for an oversized inline clip, or should a Vision-specific code be defined?
